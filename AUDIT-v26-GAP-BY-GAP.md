### Top 5 most critical gaps

1. **§3.2 / §0.1 / §10.2 — MTQ is NOT disabled-by-default in code** (CONTRADICTS, P0).
   The public endpoints `src/app/api/mint/route.ts` and `src/app/api/testnet/mint/route.ts` happily mint MTQ on demand — there is NO `MTQ_ENABLED=false` gate, NO `productionAuthorized` check, NO F3 (Monetary Authorization) check, NO G6 (Backing/Custody/Accounting) check before minting. "MTQ is disabled" is only a marketing slogan in `src/app/legal/page.tsx` and `src/app/about/page.tsx`; the actual mint code path is wide open to anyone who can POST `{ amountUsd, participant }`.

2. **§3.4 / §3.5 / §1.7 — The "130% backing specification" pillar and 80% fiat / 18% gold / 2% digital composition are actively coded as live policy** (CONTRADICTS, P0).
   `src/app/page.tsx:147` advertises "130% backing specification" as a Platform Pillar; `src/lib/mtq-final-reserve-spec.ts:63-68` hardcodes `RR_strategic: 1.30, RR_policy_floor: 1.05, RR_floor: 1.00, emergencyCapacityMax: 0.20, fiatPct: 0.80, goldPct: 0.18, digitalPct: 0.02`; `src/components/final-reserve-spec-dashboard.tsx:792` says "130% institutional backing target → 80% monetary/fiat + 18% gold-centered bullion + 2% digital liquidity". v26.0 §3.4 explicitly says these historical parameters are "DEFERRED, NOT ACTIVE", "Pilot A uses none of these parameters and keeps MTQ disabled. Pilot B must not inherit them by default."

3. **§6.1 / §6.2 / D-006 — Turso is treated as authoritative financial writer; Neon is a "fallback"** (CONTRADICTS, P0).
   `src/lib/db.ts:31-32, 445-464` establishes Turso as the PRIMARY authoritative database and Neon as a MANUAL FALLBACK engaged via `DATABASE_BACKEND=neon`. v26.0 §6.1/§6.2 explicitly mandates the OPPOSITE: "Neon is the proposed canonical write authority for transaction/obligation state. Turso can host projections and permitted demo/local data but must not independently commit authoritative financial settlement. If the code treats both databases as co-equal writers, that is a P0 architecture conflict; block real-value operation until resolved." There is NO outbox, NO projector with `lastAppliedEventId/sequence/watermark`, NO dispatcher claiming pending outbox rows. This is the canonical §6.2 split-brain anti-pattern in production.

4. **§3.3 — Eligible Backing formula is wrong** (CONTRADICTS, P0).
   v26.0 §3.3 mandates `EligibleBacking = MIN(EconomicBacking, LegalBacking, LiquidBacking, SettlementAvailableBacking)` — a 4-input cap. The code implements a DIFFERENT 8-input formula `DMCE = MIN(VerifiedEligibleBacking, LegallyReservedBacking, InstitutionalRiskLimit, LiquidityLimit, JurisdictionLimit, ExposureLimit, ConcentrationLimit, OperationalLimit)` in `src/lib/final-integrated-architecture.ts:1025-1132` and `src/lib/protected-backing-cell.ts:260` uses a third formula `AvailableBacking = RecognizedBacking − EncumberedBacking − AlreadyAllocatedBacking`. None of these match the canonical §3.3 formula. The four-input structure (each input carries amount/unit/as-of/evidence/freshness/legal scope/status) is not modeled anywhere.

5. **§4.2 / §4.4 — The F0–F7 finality state machine is NOT implemented; BM-15/BM-16A/BM-16B canonical naming is contradicted** (CONTRADICTS, P0).
   No file implements the F0 through F7 finality states (F0 Instruction accepted, F1 Bank funding final, F2 Legally controlled backing confirmed, F3 MITHQAL monetary authorization, F4 Ledger state committed, F5 Receiving institution accepted, F6 External rail final, F7 Legal settlement final) with their minimum proof predicates and failure behaviors. `src/lib/v24-2-state-machine.ts` is a 6-state RESERVE stress state machine (NORMAL→CAUTION→DEFENSIVE→STRESS→EMERGENCY→RECOVERY), not the finality machine. `src/lib/mtq-os/index.ts:25` says `BM-16: Finality Verification + Mint` (legacy combined name) and `src/lib/final-integrated-architecture.ts:1184` says `BM-15 — MITHQAL executes Mint Permission Engine` (legacy "Mint Permission Engine" name explicitly prohibited by §4.4). The canonical BM-16A/BM-16B split does not exist in code.

### Overall verdict

The MITHQAL repository is an impressively-engineered marketing and design-artifact platform with extensive institutional documentation (287 files under `institutional/`) and ~130 TypeScript lib modules — but when measured against the v26.0 Canonical Master Blueprint as a *normative* specification, the implementation fails on its most safety-critical commitments. The home page itself contradicts the blueprint ("130% backing specification" as a Platform Pillar), the live mint API path is not disabled despite all marketing text saying so, Turso is the authoritative writer (the opposite of D-006), the F0–F7 finality state machine and BM-16A/BM-16B canonical naming are not implemented, and 9 of the 12 canonical repository deliverable paths (`docs/canonical/`, `docs/adr/`, `docs/controls/`, `schemas/`, `policies/`, `migrations/`, `inngest/`, `institutional/evidence/`, `institutional/gates/`, `institutional/incidents/`) DO NOT EXIST. The repository has all the institutional-disclosure honesty machinery at the documentation layer (ProgramStatus, honest-state JSON files, G0=G11 gate ledger at `institutional/execution/institutional-gate-status.json`), but the runtime code is not aligned with v26.0 — it is still aligned with v25.3 / v25.6 legacy design. To reach Pilot A readiness (§11.1 Phase 4), the home page must be re-voiced, the mint API must be hard-gated to fail-closed by default, the historical reserve parameters must be relabeled as DEFERRED, the database writer must be flipped to Neon+outbox, and the F0–F7 + BM-16A/BM-16B canonical model must be built.
