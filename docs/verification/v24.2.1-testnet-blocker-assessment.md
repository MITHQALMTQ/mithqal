### Blocker 3 — Unresolved cross-chain supply invariant → **PARTIALLY RESOLVED**

**Evidence** (re-verified 2026-08-14 by `scripts/cross-chain-supply-invariant.py`):

```
MonadOutstanding              =     310.949000 MTQ
ArcOutstanding                =   1,000.000000 MTQ
SolanaOutstanding             =      18.446744 MTQ   (see note below)
LockedBridgeRepresentation    =       0.000000 MTQ   (no bridge contract deployed)
-------------------------------------------------------
TotalAuthorizedOutstanding     =   1,329.395744 MTQ

Blueprint authorized ceiling  =  54,000,000.000000 MTQ
On-chain total                =       1,329.395744 MTQ  (0.0025% of ceiling)
Over-authorization            =  -53,998,670.604256 MTQ (under ceiling — expected)
```

**Invariant checks**:
| Check | Status |
|---|:---:|
| All chain supplies readable | ✅ True |
| Sum ≤ blueprint ceiling | ✅ True |
| Bridge accounting complete (locked_bridge = 0) | ✅ True (trivially — no bridge deployed) |
| No known duplicate MTQ across chains | ✅ True (independent native mints) |
| §51 invariant status | **VERIFIED** (compositionally) |

**Yellow flag (informational)**: The Solana MTQ mint supply field reads `18446744073709551615` raw = `2^64 − 1` (UINT64_MAX). Divided by `10^18` decimals this yields ~18.446744 MTQ. This value is suspicious:
- Either the mint authority intentionally set the supply field to `UINT64_MAX` as a sentinel (e.g., to mark the mint as "uncapped" — NOT a standard SPL pattern), or
- An accidental max-mint occurred during deployment.
- Regardless: the supply field is **saturated**, meaning no further SPL minting is possible (any mint call would overflow u64 and revert). The "18.45 MTQ" figure is an artifact of dividing `UINT64_MAX` by `10^18`, not a real circulating supply measurement.

**Why PARTIALLY RESOLVED**:
- The compositional invariant (sum = sum of native supplies, no double-counting) holds because each chain has an independent native MTQ mint and no bridge contract is deployed → no cross-chain locking → no possibility of duplicate unlocked representations.
- BUT the directive §51 explicitly requires a canonical bridge architecture with **bridge lock** / **bridge release** / **finality** / **replay protection** / **authority**. None of these bridge primitives exist on-chain today.
- The invariant is trivially conserved **because cross-chain transfers are not yet possible**. The moment a bridge is deployed, locked-canonical accounting MUST be added or the invariant becomes "unlocked MTQ on chain A + unlocked duplicate MTQ on chain B" — exactly what §51 forbids.

**Status**: PARTIALLY RESOLVED. The invariant holds today (compositionally) but the production bridge architecture required by §51 is NOT implemented. Mainnet requires deploying a canonical bridge-lock contract before enabling cross-chain transfers.

### Blocker 8 — Unresolved ERTF accounting problem → **PARTIALLY RESOLVED**

**Evidence** (from `docs/blueprint/mithqal-canonical-blueprint.md` §V24.2.10 and `docs/verification/emergency-reserve-mode-report.md`):

**Spec/model** (canonical, RESOLVED):
- §V24.2.10 ERTF definition: legally separate, independently governed, **non-reserve** (does NOT count toward R_a), **non-PAR** (does NOT affect PAR), **non-monetary** (NOT required for ordinary MTQ redemption).
- Formula: `NetRecovery = PolicyLimit × TriggerProbability × RecoveryFactor`
- Current coverage: $10,000,000 total, $5,905,000 expected recovery (59.05% — reflects basis risk and counterparty risk).
- §V24.2.11 In-Kind Emergency Reserve Delivery: `InKindValue = MarketValue(DeliveredAssets)`, NOT `PAR`. Correctly does NOT guarantee 100% PAR.
- The §46 deterministic Test D ("5% custody + 100% LGD + ERTF unavailable → 96.90% MUST FAIL") confirms the ERTF accounting model is correctly implemented: when ERTF=0 cover, the loss flows through to RR exactly as the model specifies. ERTF being *non-reserve* (does not inflate R_a) is the key accounting property — and it holds.

**Runtime gap** (NOT YET RESOLVED):
- Gap G7 (`docs/verification/emergency-reserve-mode-report.md` §"Gap: Emergency State Not Persisted"): `declareEmergency()` returns a state object but does **not** write to the database, set an on-chain flag, or expose an API endpoint. Emergency state is in-memory only.
- This means: if the process restarts mid-emergency, the emergency state is lost. The accounting MODEL is correct, but the RUNTIME persistence of emergency declarations is incomplete.

**Status**: PARTIALLY RESOLVED. The ERTF accounting MODEL (formula, non-reserve classification, non-PAR classification, in-kind delivery formula) is correctly specified and the §46 Test D proves the accounting behaves correctly under stress. The RUNTIME persistence (G7 gap) is incomplete — `declareEmergency()` does not persist state. Recommendation: add DB persistence + on-chain flag + API endpoint for emergency state.
